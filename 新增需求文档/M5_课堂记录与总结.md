## 一、功能描述

本册合并了两条需求，因为它们是**同一页的两个部分**：

**课堂记录（需求 3）**
- 记录**发言区**内容
- 记录**每个学生与 AI 的聊天记录**（**没聊过的不显示**）
- 打上"课堂 + 课件"的区分

**课堂总结（需求 4）**
- **仅基于聊天记录**生成（不掺课件和知识点）

## 二、接口设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/session/{id}/record/overview` | 教师 / 管理员 | 概览：时长、参与人数、发言数、AI 问答数 |
| GET | `/api/session/{id}/record/chat` | 教师 / 管理员 | 发言时间线（分页） |
| GET | `/api/session/{id}/record/qa` | 教师 / 管理员 | **按学生分组的 AI 问答，只返回聊过的学生** |
| POST | `/api/session/{id}/summary` | 教师 / 管理员 | 触发生成总结（异步） |
| GET | `/api/session/{id}/summary` | 教师 / 管理员 | 获取总结（含状态） |

### 关键：只返回聊过的学生

```jsonc
// GET /api/session/{id}/record/qa
{ "code": 0, "message": "ok", "data": { "students": [
  { "userId": 7, "nickname": "演示同学", "askCount": 5,
    "records": [
      { "id": 301, "pageNo": 12, "question": "...", "answer": "...",
        "askedAt": "2026-09-20T22:10:00" }
    ] } ] } }
```

> **没有提问记录的学生不会出现在 `students` 数组里** —— 直接对应 Friday 的要求「**没有与 AI 聊天的则不显示**」。
>
> 实现上很简单：SQL 用 `INNER JOIN` 而非 `LEFT JOIN`，没记录的学生自然不出现。

```jsonc
// GET /api/session/{id}/summary
{ "code": 0, "message": "ok", "data": {
  "status": "SUCCESS", "content": "本堂课主要围绕...",
  "generatedAt": "2026-09-20T22:20:00", "errorMessage": null } }
```

## 三、技术方案

### 3.1 课堂记录

| 关注点 | 做法 |
|---|---|
| **数据源** | 发言来自 `chat_message`（M2）、AI 记录来自 `qa_record`（M4）。**都不新建存储** |
| **"没聊过不显示"** | SQL 用 `INNER JOIN`，没记录的学生自然不出现 |
| **概览数字** | 参与人数取 `session_participant`，发言数取 `chat_message`，问答数取 `qa_record` |

### 3.2 课堂总结

| 关注点 | 做法 |
|---|---|
| **异步生成** | 仿照现有 `AiParseService` 的模式：立即返回，后台跑，前端轮询状态 |
| **独立线程池** | 新增 `summaryExecutor`（**单线程**）。**不与 `aiParseExecutor` 共用** —— 否则大课件解析时总结会排队 |
| **总结来源** | **仅** `chat_message` + `qa_record` 的文本。**不含课件、不含知识点**（按需求 4 明确限定） |
| **无记录处理** | 两类记录都为空 → 回 `BIZ_SUMMARY_EMPTY`，**不调模型**（防白花钱） |
| **重复触发** | `status=RUNNING` 时回 `BIZ_SUMMARY_RUNNING`，**不重复调模型** |
| **超长处理** | 按 Friday 指示**不做分块**。总字符数超阈值时**直接截断**，并在结果里标注"记录过长，已截断" |
| **存储** | 写入已有 `course_summary` 表（`session_id` 已有唯一键，天然一课堂一份） |
| **模型调用** | 新增 `CallKind.SUMMARY`：较长超时（60s）、较大 `max_tokens`、**低温度**（要稳定不要创意） |

### 3.3 总结提示词要点

- **角色**：你是课堂记录整理助手
- **输入**：本堂课的讨论区发言 + 学生与 AI 的问答
- **输出结构**：
  1. 课堂讨论的主要话题
  2. 学生集中困惑的点
  3. 值得老师关注的问题
- **硬性要求**：**不得编造记录中不存在的内容**

## 五、开发步骤

| # | 步骤 | 验收 |
|---|---|---|
| M5-1 | 概览接口 + 页面骨架 | 能看到时长 / 人数 / 发言数 |
| M5-2 | 发言时间线 | 内容与讨论区一致，按时间正序 |
| M5-3 | 分学生的 AI 问答（**只显示聊过的**） | 建两个学生，只有一个提问 → **只显示那一个** |
| M5-4 | 总结异步生成（含超长截断、空记录拦截） | 点生成 → 轮询 → 出结果 |
| M5-5 | 记录页入口串联 | 从课堂 / 课件详情能跳进来 |

## 六、验收标准

- [ ] 课堂记录里能看到**全部发言**，时间顺序正确
- [ ] **没跟 AI 聊过的学生完全不出现**（明确验证）
- [ ] 学生 A 聊过、学生 B 没聊过 → 只显示 A
- [ ] 点「生成总结」，**30 秒内**出结果
- [ ] 无任何记录时点生成 → 提示"本堂课无记录"，**不产生模型调用**
- [ ] 重复点生成**不会重复调用模型**
- [ ] 总结内容**不包含**课件知识点（只基于聊天记录）
