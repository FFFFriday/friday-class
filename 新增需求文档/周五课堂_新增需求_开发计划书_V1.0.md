## 〇、文档说明

### 0.1 本文档要解决什么

Friday 一次性提出了 8 条新需求，**顺序是乱的、颗粒度不一、彼此有隐含依赖**。本文档做三件事：

1. **整理需求顺序** —— 把 8 条原始需求重排成有依赖关系的 7 个模块；
2. **给出数据库建模** —— 新增 4 张表、修改 3 张表，含完整可执行 DDL；
3. **给出逐模块的接口设计 + 技术方案 + 开发步骤 + 验收标准**。

### 0.2 已确认的边界条件（前置约束，不再讨论）

| 项 | 决定 | 影响 |
|---|---|---|
| 演示环境 | **只用 localhost** | 屏幕共享无障碍（`getDisplayMedia` 仅安全上下文可用，localhost 属安全上下文） |
| 音频 | **只要老师麦克风**，不要 PPT/系统声音 | 绕过 Chrome 系统音频捕获限制 |
| 并发规模 | **最多 2 个学生接收** | 不做多路扇出优化、不引入 SFU/媒体服务器 |
| 对话长度 | 不演示长对话 | 上下文只做**窗口兜底**，不做摘要压缩 |
| 聊天记录量 | 不演示大量记录 | 总结**单次调用**，不做分块 map-reduce |
| 管理端范围 | 用户 / 课堂 / 课件与存储 **三组**；AI 成本统计**删除** | 审计日志按指示**保留** |
| 测试 | 不搞全项目覆盖，只写**验证新功能的脚本** | 不做漏洞彻查 |
| 端口 | 前端固定 **5173** | 后端 CORS 不动 |
| 数据迁移 | **不搬任何老数据**，只加新表新列 | 老记录原样保留 |
| 省钱优化 | **全部删除**（答案复用 + 并发合流） | 消除上下文串台问题 |
| WebRTC 方案 | **纯 P2P，不新增独立服务** | 信令复用现有 WebSocket |

### 0.3 术语速查（给不写代码的人看）

| 术语 | 一句话解释 |
|---|---|
| **P2P** | 点对点直连。老师的浏览器直接把画面传给学生的浏览器，不经过服务器中转 |
| **信令** | 建立直连前的"交换名片"过程（互相告知地址和能力）。我们用现有 WebSocket 承担 |
| **SFU** | 媒体服务器。腾讯会议用的方案，所有流经过服务器中转分发。**本项目不用** |
| **幂等** | 同一个操作执行多次，结果和执行一次相同。数据库迁移脚本必须幂等 |
| **软删除** | 不真删数据，只把 `deleted` 标记置 1。本项目 `user`/`courseware`/`class_session` 都用这个模式 |

## 一、需求整理（把乱序的 8 条重排）

### 1.1 原始 8 条 → 模块归类

| 原始编号 | 原始描述 | 归入模块 |
|---|---|---|
| 5 | 不要 PPT 同步，要学生能看到老师屏幕 + 传输音频 | **M1 实时课堂传输** |
| 2 | 课堂上需要打字发言讨论区 | **M2 课堂讨论区** |
| 6 | 学生看不到 PPT 经 AI 解析后的内容，学生也要看到 | **M3 学生端知识可见** |
| 8 | 学生下课也能用 AI；AI 不能每次登录都是新的；要会话管理和上下文记忆 | **M4 学生 AI 会话** |
| 3 | 记录课堂内容：发言区内容 + 各学生与 AI 的聊天记录（没聊的不显示） | **M5 课堂记录** |
| 4 | 课堂总结功能（仅针对聊天记录） | **M5 课堂记录** |
| 1 | 管理端：管理课堂、账号、存储的数据，随时暂停所有课堂等 | **M6 管理端** |
| 7 | 更好的 UI 界面（CSS，可后置） | **M7 界面美化** |

### 1.2 依赖关系（为什么必须这个顺序）

```
        ┌──────────────────────────────────────────┐
        │  P0 地基（无可见变化）                     │
        │  · 新建 4 表 / 改 3 表                    │
        │  · ADMIN 角色                             │
        │  · WebSocket 升级为双向 + 带用户身份       │
        │  · CSS 设计令牌                           │
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────┴──────────────────────────┐
        │  P1 实时核心   M1 屏幕+音频   M2 讨论区    │  ← 风险最高，先做
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────┴──────────────────────────┐
        │  P2 学生 AI    M4 会话    M3 知识可见      │
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────┴──────────────────────────┐
        │  P3 记录总结   M5（依赖 M2 的发言 + M4 的AI记录）
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────┴──────────────────────────┐
        │  P4 管理端     M6（依赖 P0 的 ADMIN 角色 + P1 的暂停状态）
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────┴──────────────────────────┐
        │  P5 UI 收口    M7（套用 P0 令牌，回填老页面）
        └──────────────────────────────────────────┘
```

**排序理由（说人话）：**

- **P0 必须最先**：后面每个模块都要用新表、新角色、新 WebSocket 能力。地基不做，上面全是空中楼阁。
- **P1 排在前面**：屏幕传输是**唯一有技术不确定性**的部分。万一有坑，越早发现越好，不能拖到最后。
- **P2 在 P3 之前**：课堂记录要记录"学生和 AI 聊了什么"，先得有会话体系。
- **P4 在 P1 之后**：管理端的"暂停所有课堂"依赖 P1 定义好的课堂状态机。
- **P5 最后**：UI 是横切关注点，等页面都长出来了再统一回填，避免返工。

### 2.2 新增 4 张表

#### 2.2.1 `chat_message` —— 课堂讨论区发言

```sql
CREATE TABLE IF NOT EXISTS `chat_message` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '发言ID',
  `session_id`  BIGINT UNSIGNED NOT NULL                COMMENT '所属课堂',
  `user_id`     BIGINT UNSIGNED NOT NULL                COMMENT '发言人',
  `page_id`     BIGINT UNSIGNED NULL                    COMMENT '发言时所在页（用于关联知识点，可空）',
  `content`     VARCHAR(1000)   NOT NULL                COMMENT '发言内容（纯文本，禁止 HTML）',
  `status`      VARCHAR(20)     NOT NULL DEFAULT 'NORMAL' COMMENT 'NORMAL / DELETED',
  `deleted_by`  BIGINT UNSIGNED NULL                    COMMENT '删除人（老师或管理员）',
  `deleted_at`  DATETIME        NULL                    COMMENT '删除时间',
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_chat_session` (`session_id`, `id`),
  KEY `idx_chat_user`    (`user_id`),
  CONSTRAINT `fk_chat_session` FOREIGN KEY (`session_id`) REFERENCES `class_session` (`id`) ON DELETE CASCADE,
  CONSTRAINT `fk_chat_user`    FOREIGN KEY (`user_id`)    REFERENCES `user` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='课堂讨论区发言';
```

**设计说明：**
- `page_id` 记录"这条发言是在第几页说的"，让课堂记录和总结能带上页面上下文。
- 用 `status='DELETED'` 软删除，保留审计痕迹。
- 索引 `(session_id, id)` 支持"按课堂拉取发言、按 id 增量拉取"。

#### 2.2.2 `ai_conversation` —— 学生 AI 会话

```sql
CREATE TABLE IF NOT EXISTS `ai_conversation` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '会话ID',
  `student_id`    BIGINT UNSIGNED NOT NULL                COMMENT '所属学生',
  `title`         VARCHAR(100)    NOT NULL DEFAULT '新会话' COMMENT '会话标题（可重命名）',
  `courseware_id` BIGINT UNSIGNED NULL                    COMMENT '关联课件（可空，空=自由问答）',
  `session_id`    BIGINT UNSIGNED NULL                    COMMENT '创建时所处课堂（可空=课后创建）',
  `last_active_at` DATETIME       NULL                    COMMENT '最后活跃时间（用于排序）',
  `deleted`       TINYINT(1)      NOT NULL DEFAULT 0      COMMENT '软删除',
  `created_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_conv_student` (`student_id`, `deleted`, `last_active_at`),
  CONSTRAINT `fk_conv_student` FOREIGN KEY (`student_id`) REFERENCES `user` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='学生AI会话';
```

**设计说明：**
- **会话归属学生**（`student_id`），学生可建多个、可切换、可重命名、可删除 —— 对应 Friday 要求的"像豆包/GPT 那样"。
- **会话之间上下文完全隔离**，互不引用。
- `courseware_id` / `session_id` 只是"创建时的来源标记"，用于筛选和归档，**不作为上下文边界**。

#### 2.2.3 `session_participant` —— 课堂参与记录

```sql
CREATE TABLE IF NOT EXISTS `session_participant` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `session_id` BIGINT UNSIGNED NOT NULL,
  `user_id`    BIGINT UNSIGNED NOT NULL,
  `role`       VARCHAR(20)     NOT NULL COMMENT '进入时的角色 TEACHER/STUDENT',
  `joined_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `left_at`    DATETIME        NULL     COMMENT '离开时间，NULL=仍在场',
  `last_seen_at` DATETIME      NULL     COMMENT '最后心跳时间（用于断线判定）',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_part_session_user` (`session_id`, `user_id`),
  KEY `idx_part_user` (`user_id`),
  CONSTRAINT `fk_part_session` FOREIGN KEY (`session_id`) REFERENCES `class_session` (`id`) ON DELETE CASCADE,
  CONSTRAINT `fk_part_user`    FOREIGN KEY (`user_id`)    REFERENCES `user` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='课堂参与者（在线名单+出席统计）';
```

**设计说明：**
- 一个学生在一节课里**只有一行**（唯一键），反复进出只更新 `left_at`/`last_seen_at`。
- 同时支撑三个用途：① 课堂实时在线名单；② 管理端"在线人数/踢人"；③ 课堂记录的"哪些学生来过"。

#### 2.2.4 `admin_audit_log` —— 管理操作日志

```sql
CREATE TABLE IF NOT EXISTS `admin_audit_log` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `admin_id`    BIGINT UNSIGNED NOT NULL COMMENT '操作人',
  `action`      VARCHAR(50)     NOT NULL COMMENT '动作码，如 SESSION_FORCE_END',

  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),

  KEY `idx_audit_action` (`action`, `created_at`),
  CONSTRAINT `fk_audit_admin` FOREIGN KEY (`admin_id`) REFERENCES `user` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='管理操作审计日志';
```

**设计说明：** 按 Friday 指示**保留**。只做"写 + 查"，不配统计页面。动作码约定见 §3.3。

### 2.3 修改 3 张表

#### 2.3.1 `class_session` —— 支持暂停、记录结束方

```sql
ALTER TABLE `class_session`
  ADD COLUMN `paused_at`  DATETIME        NULL COMMENT '暂停时间，NULL=未暂停',
  ADD COLUMN `ended_by`   BIGINT UNSIGNED NULL COMMENT '结束人，NULL=老师自己下课',
  ADD COLUMN `end_reason` VARCHAR(100)    NULL COMMENT '结束原因，如 ADMIN_FORCE';
```

- `status` 取值扩展为：`NOT_STARTED` → `LIVE` ⇄ `PAUSED` → `ENDED`（枚举在 Java 侧加 `PAUSED`）。
- `ended_by`/`end_reason` 让"管理员强制下课"可追溯。

#### 2.3.2 `qa_record` —— 挂上会话与课件

```sql
ALTER TABLE `qa_record`
  MODIFY COLUMN `page_id` BIGINT UNSIGNED NULL COMMENT '所属页，NULL=课后提问（不在任何页上）',
  ADD COLUMN `conversation_id` BIGINT UNSIGNED NULL COMMENT '所属AI会话',
  ADD COLUMN `courseware_id`   BIGINT UNSIGNED NULL COMMENT '所属课件（直连，避免两跳join）',
  ADD KEY `idx_qa_conversation` (`conversation_id`, `id`),
  ADD KEY `idx_qa_session_student` (`session_id`, `student_id`);
```

**⚠️ 最重要的一条**：`page_id` 必须能空。学生下课后问 AI 时**不在任何一页上**，若保持 `NOT NULL`，课后问答**直接落库失败**。

#### 2.3.3 `course_summary` —— 支持异步生成

```sql
ALTER TABLE `course_summary`
  ADD COLUMN `status`        VARCHAR(20) NOT NULL DEFAULT 'SUCCESS' COMMENT 'PENDING/RUNNING/SUCCESS/FAILED',
  ADD COLUMN `error_message` TEXT        NULL COMMENT '失败原因',
  ADD COLUMN `source`        VARCHAR(20) NOT NULL DEFAULT 'SESSION_CHAT' COMMENT '总结来源',
  MODIFY COLUMN `content` TEXT NULL COMMENT '总结正文';
```

- 表已有 `session_id`（唯一键）→ 天然满足"一个课堂一份总结"。
- `source` 预留：本次只做 `SESSION_CHAT`（仅基于聊天记录），未来若要"课件+知识点+问答全量总结"可扩展。

--    MySQL 8.0 不支持 ADD COLUMN IF NOT EXISTS，故先查 information_schema 再改
DROP PROCEDURE IF EXISTS `fc_add_column`;

CREATE PROCEDURE `fc_add_column`(
  IN p_table VARCHAR(64), IN p_col VARCHAR(64), IN p_ddl TEXT)
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.COLUMNS
    WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = p_table AND COLUMN_NAME = p_col
  ) THEN
    SET @s = CONCAT('ALTER TABLE `', p_table, '` ADD COLUMN ', p_ddl);
    PREPARE st FROM @s; EXECUTE st; DEALLOCATE PREPARE st;
  END IF;
END$$
DELIMITER ;

| `idx_chat_session (session_id, id)` | `chat_message` | 按课堂拉发言；`id > ?` 增量拉新 |

| `idx_qa_conversation (conversation_id, id)` | `qa_record` | 组装某会话的上下文（倒序取最近 N 轮） |
| `idx_qa_session_student (session_id, student_id)` | `qa_record` | 课堂记录：按课堂+学生分组 |
| `uk_part_session_user (session_id, user_id)` | `session_participant` | 保证一人一行；在线名单 |

## 三、全局技术约定

### 3.1 WebSocket 消息协议 v2

现有 `/ws/page` 是**裸 TextWebSocketHandler、单向下行**（刻意设计：保证老师翻页不被掉线 socket 卡住）。V2 扩展为**双向**，但守住一条边界：

> **翻页继续走 POST 不变，WebSocket 只新增「下行事件」和「上行聊天」。**
> 聊天丢一条无所谓，翻页不能丢。

**客户端 → 服务端**

| type | 载荷 | 说明 |
|---|---|---|
| `auth` | `{token}` | **已有**。连接后 5 秒内必须发，否则断开 |
| `ping` | `{}` | **已有** |
| `chat.send` | `{content, clientMsgId}` | **新增**。发讨论区消息 |
| `webrtc.answer` | `{toUserId, sdp}` | **新增**。学生回信令 |
| `webrtc.ice` | `{toUserId, candidate}` | **新增**。双方 ICE 候选 |
| `webrtc.ready` | `{}` | **新增**。学生表示"可以接流了" |

**服务端 → 客户端**

| type | 载荷 | 说明 |
|---|---|---|
| `auth_ok` | `{sessionId, userId, role, online}` | **已有**（`online` 含义扩展为参与者数） |
| `page` | `{pageNo, serverTime}` | **已有** |
| `ended` | `{serverTime}` | **已有** |
| `pong` | `{}` | **已有** |
| `error` | `{message}` | **已有** |
| `chat.new` | `{id, userId, nickname, content, createdAt}` | **新增** |
| `chat.deleted` | `{id}` | **新增** |
| `presence.join` | `{userId, nickname, role, online}` | **新增** |
| `presence.leave` | `{userId, nickname, online}` | **新增** |
| `stream.started` | `{teacherId}` | **新增**。老师开始共享 |
| `stream.stopped` | `{}` | **新增** |
| `class.paused` / `class.resumed` | `{by}` | **新增** |
| `kicked` | `{reason}` | **新增**。被踢，前端提示并断开 |
| `webrtc.offer` | `{fromUserId, sdp}` | **新增**。老师发给指定学生 |
| `webrtc.ice` | `{fromUserId, candidate}` | **新增** |

**实现要点：**
- `SessionRegistry` 从 `Map<sessionId, Set<WebSocketSession>>` 升级为 `Map<sessionId, Map<userId, Participant>>`，`Participant` 含 `userId / role / session / joinedAt`。
- 新增"**定向发送**"能力（信令、踢人需要发给特定人）—— 现有只有广播。
- 未认证连接的 1 秒清扫线程**保持不动**。

### 3.2 权限模型

| 层 | 规则 |
|---|---|
| 后端 | **唯一边界**。`/api/admin/**` → `hasRole('ADMIN')`（在 `SecurityConfig` 显式配置，deny-by-default） |
| 前端 | 路由守卫仅 UX，**不算安全边界**（沿用项目既有约定） |
| 新增角色 | `Role.ADMIN`。按项目既有策略：**注册只建学生，教师与管理员由 SQL 预置** |

### 3.3 审计动作码约定

| 动作码 | 含义 |
|---|---|
| `USER_CREATE` / `USER_DISABLE` / `USER_ENABLE` / `USER_RESET_PWD` / `USER_CHANGE_ROLE` / `USER_DELETE` | 用户管理 |
| `SESSION_FORCE_END` / `SESSION_PAUSE` / `SESSION_RESUME` / `SESSION_PAUSE_ALL` / `SESSION_END_ALL` / `SESSION_KICK` | 课堂管理 |
| `COURSEWARE_DELETE` / `COURSEWARE_REPARSE` | 课件管理 |
| `STORAGE_ORPHAN_CLEAN` | 存储清理 |

### 3.4 错误码

沿用现有 `ApiResponse{code,message,data}` 信封。新增业务码：

| code | 含义 |
|---|---|
| `BIZ_RATE_LIMITED` | 触发限流（讨论区发言 / AI 提问） |
| `BIZ_CONVERSATION_NOT_FOUND` | 会话不存在或不属于当前用户 |
| `BIZ_SESSION_NOT_LIVE` | 课堂不在进行中 |
| `BIZ_STREAM_NOT_AVAILABLE` | 当前无共享流 |
| `BIZ_SUMMARY_EMPTY` | 无聊天记录，无法生成总结 |
| `BIZ_SUMMARY_RUNNING` | 总结正在生成中 |

### M1 · 实时课堂传输（屏幕 + 麦克风音频）

#### M1.1 功能描述

老师在自己的浏览器里共享**画面**和**麦克风声音**，学生端实时观看/收听，替代原来的"PPT 图片翻页同步"。

**明确的边界：**
- 学生看到的是**老师的屏幕内容**（可以是老师的 PPT，也可以是任何东西）
- 学生听到的是**老师的麦克风**，不是 PPT 里的声音
- 老师在**我们自己的网页幻灯片**上讲课 → 程序天然知道当前页码 → AI 知识点对齐零误差

#### M1.2 接口设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/session/{id}/stream` | **仅教师** | body `{live: true/false}`。开始/停止共享的状态登记，成功后广播 `stream.started`/`stream.stopped` |
| GET | `/api/session/{id}/stream` | 需登录 | 查询当前是否有共享流（学生进入课堂时用） |

**信令本身不走 REST，走 WebSocket**（见 §3.1）。

```jsonc
// POST /api/session/{id}/stream 请求
{ "live": true }

// 响应（统一信封）
{ "code": 0, "message": "ok",
  "data": { "live": true, "startedAt": "2026-09-20T22:00:00" } }
```

**错误**：`BIZ_SESSION_NOT_LIVE`（课堂不在进行中）、403（非本课堂教师）

#### M1.3 技术方案

**技术选型：WebRTC 点对点（P2P），信令走现有 WebSocket。不引入任何独立媒体服务。**

| 环节 | 做法 |
|---|---|
| 采集 | 老师端 `getDisplayMedia({video:{frameRate:20}})` 取画面；`getUserMedia({audio:true})` 取麦克风。两条轨道合成一个 `MediaStream` |
| 建连 | 老师为**每个学生**建一条 `RTCPeerConnection`（演示场景 ≤2 人，不做 SFU） |
| 信令 | offer/answer/ICE 封装成 §3.1 的消息，经现有 `/ws/page` 转发，服务端只做**定向投递**，不解析内容 |
| 播放 | 学生端 `<video autoplay playsinline>`，`pc.ontrack` 时 `video.srcObject = event.streams[0]` |
| 保真 | 屏幕内容是文字，优先**清晰度**而非流畅度：限制 1080p / 20fps、`contentHint='text'`、码率上限 ~2Mbps |
| 断线 | 学生刷新 = 重新进入 → 服务端发 `presence.join` → 老师**重建该学生的连接**。不需单独的"重连"逻辑，把"首次建连"写扎实即可 |

**关键实现细节（容易踩的）：**
1. **`getDisplayMedia` 只在安全上下文可用** → localhost 可以，局域网 IP 不行。本项目只用 localhost，无影响，但失败时要有明确提示。
2. **学生端带声音的 `<video>` 自动播放会被浏览器拦截** → 必须有「进入课堂」按钮（用户手势）解锁音频。这是硬性 UX 要求，不是可选项。
3. **老师中途切换共享源时用 `replaceTrack`**，不要重建连接。
4. **服务端不解析 SDP**，只按 `toUserId` 转发，保持解耦。

|---|---|---|
| `pages/TeachPresentPage.vue` | **新建** | 纯净演示页 `/present/:sessionId`。只有幻灯片 + 页码角标，**无任何按钮**。老师共享**这个标签页**。方向键翻页 |

### M2 · 课堂讨论区

#### M2.1 功能描述

课堂内的**纯文字**讨论区。所有在场学生和老师都能发言，老师可以删除不当发言。

#### M2.2 接口设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/chat/{sessionId}/messages` | 需登录 | 拉历史。参数 `afterId`（增量）或 `beforeId`+`limit`（翻页） |
| DELETE | `/api/chat/messages/{id}` | **教师 / 管理员** | 软删除该条发言 |

**发送不走 REST，走 WebSocket `chat.send`**（低延迟）；REST 只负责"拉历史"和"删除"。

```jsonc
// GET /api/chat/{sessionId}/messages?afterId=120&limit=50
{ "code": 0, "message": "ok",
  "data": {
    "items": [
      { "id": 121, "userId": 7, "nickname": "演示同学", "role": "STUDENT",
        "content": "老师这里没听懂", "pageId": 88,
        "createdAt": "2026-09-20T22:05:11" }
    ],
    "hasMore": false
  } }
```

#### M2.3 技术方案

| 关注点 | 做法 |
|---|---|
| 传输 | 上行 `chat.send{content, clientMsgId}`；服务端落库后广播 `chat.new` 给全课堂 |
| **防重复** | `clientMsgId`（前端生成的 UUID）做**短时（60 秒）去重**，防止网络重发导致重复发言 |
| 限流 | **每人 1 条 / 2 秒**（沿用现有 `QaService` 的进程内限流写法）。超限回 `BIZ_RATE_LIMITED` |
| **XSS 防护** | 内容**纯文本存储**，前端**纯文本插值渲染**（`{{ }}`），**严禁 `v-html`** —— 项目既有铁律 |
| 长度 | 单条 ≤ 1000 字符（与表结构一致），超长截断并提示 |
| 删除 | 软删除 + 广播 `chat.deleted`，所有客户端置灰为「该发言已被老师撤回」 |
| 页码标记 | 发言时前端带上当前 `pageId`，服务端落库。让课堂记录显示"这条是在第 N 页说的" |
| 内容过滤 | **不做**关键词过滤（超出范围）。只做长度与频率限制 |

| 文件 | 动作 | 说明 |
|---|---|---|
| `components/features/ClassChatPanel.vue` | **新建** | 讨论区面板：消息列表 + 输入框 + 发送。老师视角多一个"删除"按钮 |

#### M2.5 开发步骤

| # | 步骤 | 验收 |
|---|---|---|
| M2-1 | `chat_message` 表 + 实体 + 仓库 | 能插入/查询 |

### M4 · 学生 AI 会话与上下文

#### M4.1 功能描述

- 学生有**自己的多个 AI 会话**，像豆包/GPT 一样可新建、切换、重命名、删除
- **每个会话有自己独立的上下文**，会话之间**互不引用**
- **重新登录后会话还在**（不是每次都新开一个 AI）
- **下课后依然能用**（不依赖课堂）

#### M4.2 接口设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/ai/conversations` | 学生 | 我的会话列表（按最后活跃倒序） |
| POST | `/api/ai/conversations` | 学生 | 新建会话 |
| GET | `/api/ai/conversations/{id}` | 学生 | 会话详情 + 消息列表 |
| PUT | `/api/ai/conversations/{id}` | 学生 | 重命名 |
| DELETE | `/api/ai/conversations/{id}` | 学生 | 软删除 |
| POST | `/api/qa/ask` | 需登录 | **改造**：body 增加**可选** `conversationId` |

**⚠️ 最小改动原则**：**不新建提问接口**，而是在现有 `POST /api/qa/ask` 上加一个**可选**字段：

- 传了 `conversationId` → 写进该会话
- 没传 → 自动落到该学生在该课件下的"默认会话"（找不到就建一个）

这样**现有前端不改也能继续跑**，新 UI 才传 `conversationId`。

```jsonc
// POST /api/qa/ask 请求体（改造后）
{
  "sessionId": 13,          // 可空（课后提问为空）
  "pageId": 88,             // 可空（课后提问为空）
  "conversationId": 42,     // 新增·可空
  "question": "什么是TCP三次握手",
  "clientRequestId": "uuid-xxxx"
}

// 响应（沿用现有 QaRecordResponse，增加会话信息）
{ "code": 0, "message": "ok",
  "data": {
    "id": 301, "conversationId": 42, "question": "...", "answer": "...",
    "status": "SUCCESS", "turn": 3, "askedAt": "2026-09-20T22:10:00"
  } }

// GET /api/ai/conversations
{ "code": 0, "message": "ok", "data": { "items": [
  { "id": 42, "title": "离散数学答疑", "coursewareId": 24, "sessionId": 13,
    "messageCount": 12, "lastActiveAt": "2026-09-20T22:10:00" } ] } }
```

#### M4.3 技术方案

##### ① 删除"省钱两件套"（按 Friday 指示）

`service/QaService.java` 中移除两处：

| 移除项 | 原作用 | 移除理由 |
|---|---|---|
| 答案复用缓存（`DEDUP_TTL=10min`、`MAX_CACHE_ENTRIES=2000`） | 10 分钟内相同问题复用答案 | 按指示不省钱；**且会跨会话串台**（同一问题在不同会话必须得到不同答案） |
| 并发合流（`inFlight` 单飞） | 并发同问只调一次模型 | 同上 |

**保留**：`clientRequestId` + `uk_qa_client_req` 唯一索引的幂等。
→ 这不省模型钱，是防"手抖双击重复扣费"，无害且必要。

##### ② 上下文组装

```
取该会话最近 N 轮问答（默认 N=6）→ 按时间正序拼成历史
→ 与「当前页知识点 + 预置提问 + 本次问题」一起组成 prompt
```

| 项 | 决定 |
|---|---|
| 窗口大小 | **6 轮**（可配置 `app.ai.context-turns`）。这是**兜底**，不是优化 —— 防止会话无限增长撑爆模型上下文 |
| 检索方式 | `WHERE conversation_id=? ORDER BY id DESC LIMIT 12`（6 轮 = 12 条问答），再反转为正序 |
| 超长处理 | 单轮问答超长时按字符截断（沿用现有 `PromptTemplates` 的截断策略） |
| **不做** | 摘要压缩、向量检索、跨会话引用（按 Friday 指示不做） |
| 提示词改造 | `PromptTemplates.qaUserPrompt(...)` 增加 `history` 参数，历史部分同样走 `sanitize()` 包裹，防注入 |

##### ③ 课后可用

- 提问时 `sessionId`/`pageId` 允许为空（依赖 §2.3.2 把 `page_id` 改成可空）
- 课后入口：新页面 `/ai`（会话列表）与 `/ai/:conversationId`（聊天），以及课件详情页的「问 AI」按钮

##### ④ 成本与限额（不省钱，但要防失控）

- 每人提问上限沿用现有 **1 问 / 5 秒**
- 单会话消息数上限 **200 条**（超出提示"本会话太长，建议新建"）—— 防止单会话无限膨胀
- `CallKind.QA` 的 `max_tokens` 保持不变

#### M5.2 接口设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/session/{id}/record/overview` | 教师 / 管理员 | 概览：时长、参与人数、发言数、AI 问答数 |
| GET | `/api/session/{id}/record/chat` | 教师 / 管理员 | 发言时间线（分页） |
| GET | `/api/session/{id}/record/qa` | 教师 / 管理员 | **按学生分组的 AI 问答，只返回聊过的学生** |
| POST | `/api/session/{id}/summary` | 教师 / 管理员 | 触发生成总结（异步） |
| GET | `/api/session/{id}/summary` | 教师 / 管理员 | 获取总结（含状态） |

**关键：只返回聊过的学生**

```jsonc
// GET /api/session/{id}/record/qa
{ "code": 0, "message": "ok", "data": { "students": [
  { "userId": 7, "nickname": "演示同学", "askCount": 5,
    "records": [
      { "id": 301, "pageNo": 12, "question": "...", "answer": "...",
        "askedAt": "2026-09-20T22:10:00" }
    ] } ] } }
```

> **没有提问记录的学生不会出现在 `students` 数组里** —— 直接对应 Friday 的要求「没有与 AI 聊天的则不显示」。SQL 上用 `INNER JOIN` 天然实现（而非 `LEFT JOIN`）。

```jsonc
// GET /api/session/{id}/summary
{ "code": 0, "message": "ok", "data": {
  "status": "SUCCESS", "content": "本堂课主要围绕...",
  "generatedAt": "2026-09-20T22:20:00", "errorMessage": null } }
```

#### M5.3 技术方案

| 关注点 | 做法 |
|---|---|
| 记录数据源 | 发言来自 `chat_message`（M2）、AI 记录来自 `qa_record`（M4），**都不新建存储** |
| "没聊过不显示" | SQL 用 `INNER JOIN` 而非 `LEFT JOIN`，没记录的学生自然不出现 |
| 总结异步 | 仿照 `AiParseService` 的模式：立即返回，后台跑，前端轮询状态 |
| **独立线程池** | 新增 `summaryExecutor`（单线程）。**不与 `aiParseExecutor` 共用** —— 否则大课件解析时总结会排队 |
| 总结来源 | 仅 `chat_message` + `qa_record` 的文本。**不含课件、知识点**（按需求 4 明确限定） |
| 无记录处理 | 两类记录都为空 → 回 `BIZ_SUMMARY_EMPTY`，**不调模型**（防白花钱） |
| 重复触发 | `status=RUNNING` 时回 `BIZ_SUMMARY_RUNNING`，不重复调模型 |
| 超长处理 | 按 Friday 指示**不做分块**。总字符数超阈值时**直接截断**并在结果里标注"记录过长，已截断" |
| 存储 | 写入已有 `course_summary` 表（`session_id` 已有唯一键，天然一课堂一份） |
| 模型调用 | 新增 `CallKind.SUMMARY`：较长超时（60s）、较大 `max_tokens`、低温度（要稳定不要创意） |

**总结提示词要点：**
- 角色：你是课堂记录整理助手
- 输入：本堂课的讨论区发言 + 学生与 AI 的问答
- 输出结构：① 课堂讨论的主要话题 ② 学生集中困惑的点 ③ 值得老师关注的问题
- **明确要求：不得编造记录中不存在的内容**

| 关注点 | 做法 |
|---|---|
| **权限（最关键）** | `SecurityConfig` 增加：`requestMatchers("/api/admin/**").hasRole("ADMIN")`，且**放在白名单之后、默认 deny 之前**。**必须配套写验证脚本**证明学生调不通 |

| 强制下课 | 复用 `ClassSessionService` 的下课逻辑，额外写 `ended_by`/`end_reason`，并广播 `ended` |
| 暂停语义 | 见下方 ⚠️ |
| 踢人 | 服务端关闭该用户的 WS 连接 + 广播 `kicked{reason}` + 写 `session_participant.left_at` |
| 批量操作 | `pause-all` 等 = 查所有 `status='LIVE'` 的课堂 → 逐个执行 → **汇总返回成功/失败数**（不要因为一个失败全回滚） |
| 存储删除 | 封装 `CoursewareDeleteService`：DB（级联）+ `storage/coursewares/` + `storage/slides/{id}/` **三处一起清**，漏一处就是磁盘垃圾 |
| **孤立文件清理** | **必须先列后删**：`GET /orphans` 只返回列表，人工确认后把要删的 path 传回 `clean`。**绝不做全自动删除** —— 误删不可逆 |
| 审计 | 每个写操作后插一条 `admin_audit_log`。用 `AdminAuditService.record(action, targetType, targetId, detail)` 收口 |

**⚠️ 「暂停」的语义必须说清（重要）：**

媒体流是**点对点直连**的，服务端**管不到画面**。管理员点「暂停所有课堂」的实际效果是：

| 会发生的 | 不会发生的 |
|---|---|
| 课堂状态改为 `PAUSED` | ❌ 老师的画面**不会**被服务端切掉 |
| 广播 `class.paused`，学生端盖遮罩"课堂已被暂停" | ❌ 声音不会停 |
| 讨论区、AI 提问被禁用 | |
| 老师端收到提示，可自行停止共享 | |

**要真正停画面，必须老师端配合**（收到 `class.paused` 后停止共享轨道）。这是 P2P 架构的固有边界，不是缺陷 —— 文档和界面都要写明。
