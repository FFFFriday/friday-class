## 一、功能描述

老师在自己的浏览器里共享**画面**和**麦克风声音**，学生端实时观看/收听，替代原来的"PPT 图片翻页同步"。

**明确的边界：**
- 学生看到的是**老师的屏幕内容**（可以是老师的 PPT，也可以是任何东西）
- 学生听到的是**老师的麦克风**，不是 PPT 里的声音
- 老师在**我们自己的网页幻灯片**上讲课 → 程序天然知道当前页码 → **AI 知识点对齐零误差**

### 为什么这叫"实时"，以及它到底难不难

浏览器**自带**屏幕共享（`getDisplayMedia`）和点对点传输（`WebRTC`）。代码不需要写编解码、不碰 UDP、不碰网络穿透。真正要写的只有三步：

1. 老师点「共享屏幕」→ 拿到画面和音频
2. 学生连进来 → 双方交换一次「名片」（SDP/ICE），走**已有的 WebSocket**
3. 直连建立 → 学生的 `<video>` 直接播

**约 150 行前端 + 50 行信令转发。**

> **腾讯会议为什么看着复杂？** 因为它要解决本项目**没有**的问题：公网 + 几十人 + 弱网。
> 它必须在中间架媒体服务器（SFU）做中转混流，否则老师要往 20 个人各传一份、上行直接爆；还要 TURN 服务器穿 NAT。
> **本项目是 localhost + 2 个学生**，点对点直连就够，延迟甚至比腾讯会议还低（它还要中转一道）。

## 二、接口设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/session/{id}/stream` | **仅教师** | body `{live: true/false}`。开始/停止共享的状态登记，成功后广播 `stream.started` / `stream.stopped` |
| GET | `/api/session/{id}/stream` | 需登录 | 查询当前是否有共享流（学生进入课堂时用） |

**信令本身不走 REST，走 WebSocket**（见 `02_技术约定_WebSocket协议与权限.md` §1.2 / §1.3）。

### 请求 / 响应示例

```jsonc
// POST /api/session/{id}/stream 请求
{ "live": true }

// 响应（统一信封）
{ "code": 0, "message": "ok",
  "data": { "live": true, "startedAt": "2026-09-20T22:00:00" } }
```

**错误**：
- `403` —— 非本课堂的教师
- `BIZ_SESSION_NOT_LIVE` —— 课堂不在进行中

## 三、技术方案

**技术选型：WebRTC 点对点（P2P），信令走现有 WebSocket。不引入任何独立媒体服务。**

| 环节 | 做法 |
|---|---|
| **采集** | 老师端 `getDisplayMedia({video:{frameRate:20}})` 取画面；`getUserMedia({audio:true})` 取麦克风。两条轨道合成一个 `MediaStream` |
| **建连** | 老师为**每个学生**建一条 `RTCPeerConnection`（演示场景 ≤2 人，**不做 SFU**） |
| **信令** | offer / answer / ICE 封装成 WS 消息，经现有 `/ws/page` 转发。服务端只做**定向投递**，不解析内容 |
| **播放** | 学生端 `<video autoplay playsinline>`，`pc.ontrack` 时 `video.srcObject = event.streams[0]` |
| **保真** | 屏幕内容是文字，优先**清晰度**而非流畅度：限制 1080p / 20fps、`contentHint='text'`、码率上限 ~2Mbps |
| **断线恢复** | 学生刷新 = 重新进入 → 服务端发 `presence.join` → 老师**重建该学生的连接**。**不需要单独的"重连"逻辑**，把"首次建连"写扎实即可 |

### 关键实现细节（容易踩的）

1. **`getDisplayMedia` 只在安全上下文可用** → `localhost` 可以，**局域网 IP 不行**。本项目只用 localhost，无影响，但失败时要有明确提示。
2. **学生端带声音的 `<video>` 自动播放会被浏览器拦截** → 必须有一个「进入课堂」按钮（用户手势）来解锁音频。这是**硬性 UX 要求，不是可选项**。
3. **老师中途切换共享源时用 `replaceTrack`**，不要重建 `RTCPeerConnection`。
4. **服务端不解析 SDP**，只按 `toUserId` 转发，保持解耦。
5. **页码来自我们自己的页面** —— 老师共享的是 `/present/:sessionId` 标签页，页码由程序自己产生，**不存在"识别不准"的问题**。

### 关于"暂停课堂"与推流的关系

管理端可以暂停课堂，但**媒体流是点对点直连的，服务端管不到画面**。
详见 `M6_管理端.md` 中的「暂停语义」说明 —— 要真正停画面，需要**老师端配合**。

## 四、前端改动

| 文件 | 动作 | 说明 |
|---|---|---|
| `pages/TeachPresentPage.vue` | **新建** | 纯净演示页 `/present/:sessionId`。只有幻灯片 + 页码角标，**无任何按钮**。老师共享**这个标签页**。方向键翻页 |
| `pages/TeacherLivePage.vue` | 更新 | 加「开始共享屏幕」按钮、在线学生列表、每人的连接状态 |
| `pages/LivePage.vue` | 更新 | 加「进入课堂」手势门；`<video>` 播放老师流；**保留原幻灯片图片作为降级显示** |
| `composables/useScreenShare.js` | **新建** | 老师侧：采集 + 逐学生建连 + 轨道管理 |
| `composables/useScreenViewer.js` | **新建** | 学生侧：接收 offer/ICE、拉流、播放控制 |
| `composables/useClassSocket.js` | **新建** | 统一封装升级后的 WS（聊天、presence、信令、暂停事件）—— 现有 `usePageSync.js` 只处理翻页，功能太窄 |

### 关于"降级显示"

保留现有的「PPT 图片翻页同步」作为**手动备胎**：它不是舍不得删，而是**答辩保险** —— WebRTC 万一当场不通，演示还能继续。
这是**已有功能，不额外开发**。

## 五、开发步骤

| # | 步骤 | 产出 | 验证 |
|---|---|---|---|
| **M1-1** | **技术验证（先做，go/no-go）** | 最小闭环：老师推屏 → 学生页收到画面 | 两个浏览器标签，学生能看到老师屏幕。**不通就立即停下来商量** |
| M1-2 | `SessionRegistry` 升级 + 定向投递 | 能按 userId 发消息 | 脚本：模拟两个连接，A 定向发给 B，C 收不到 |
| M1-3 | 信令通道打通 | offer / answer / ICE 经 WS 往返 | 控制台可见完整协商日志 |
| M1-4 | 加麦克风音频 | 学生能听到老师说话 | 真人对着麦克风说话，学生端出声 |
| M1-5 | 纯净演示页 + 页码自动检测 | `/present/:id`，方向键翻页，页码广播 | 翻页时学生端页码同步、AI 知识点跟着换 |
| M1-6 | 体验打磨 | 帧率/码率/清晰度调优、断线提示 | 演示 10 分钟不卡不掉 |

> **M1-1 是整条开发路径上唯一的不确定点。**它不通，立即停下来商量备选方案（退回 PPT 图片同步 + 只做音频）。

## 六、验收标准

- [ ] 老师点「开始共享」，学生端 3 秒内出画面
- [ ] 学生能听到老师麦克风声音（点击「进入课堂」之后）
- [ ] 老师在演示页按方向键，学生端 AI 面板的知识点跟着换页
- [ ] 学生刷新页面后能自动恢复接收
- [ ] 老师停止共享后，学生端有明确提示，**不黑屏不卡死**
- [ ] 原有翻页功能仍然可用（回归）

## 七、已知限制（不是缺陷，是架构固有边界）

| # | 限制 | 说明 |
|---|---|---|
| 1 | 屏幕共享仅 `localhost` 可用 | 浏览器安全策略，换局域网 IP 会失效 |
| 2 | 音频只有麦克风 | 不含 PPT 内嵌声音 |
| 3 | 服务端无法强制停掉老师的画面 | P2P 固有特性，需老师端配合 |
| 4 | 学生数不宜过多 | 老师要为每人独立编码一份，演示场景控制在 2 人 |
